# 0001. OpenAPI is the single source of truth for the API contract

- Status: accepted
- Date: 2026-04-25

## Context

DelveMoar has three apps that need to agree on the shape of every API
request and response: the FastAPI server in `apps/api`, the React web
client in `apps/web`, and the Go CLI in `apps/cli`. Hand-written client
types in two languages would drift from the server within weeks. The
drift would show up as runtime bugs in the clients, not as compile
errors at the source of the change.

FastAPI emits an OpenAPI schema for free, derived from the Pydantic
schemas and route signatures. We need a single rule for which artifact
defines the contract.

## Decision

The API's `openapi.json` is the single source of truth. Client code in
the web app and the CLI is generated from it, never hand-written:

- `packages/api-types/src/index.ts`, generated by
  [`openapi-typescript`](https://openapi-ts.dev/), consumed by
  `apps/web` as a workspace package.
- `apps/cli/internal/apiclient/client.gen.go`, generated by
  [`oapi-codegen`](https://github.com/oapi-codegen/oapi-codegen),
  consumed by the CLI directly.

Both are regenerated by `scripts/gen_types.sh` (run via `task gen:types`).
The generated files are committed to the repo. CI re-runs the generator
on every PR and fails on any drift.

When a router signature, a Pydantic schema, or any code that affects the
emitted OpenAPI changes, the contributor regenerates and commits the
diff in the same PR.

## Considered alternatives

- **Hand-write client types in TypeScript and Go.** Fastest to start.
  Guaranteed to drift. Drift surfaces as runtime errors, not compile
  errors. Rejected.
- **Generate from a hand-written OpenAPI spec, with the API conforming
  to it.** Inverts the source of truth. Requires writing and maintaining
  a separate spec file, with no compiler to catch divergence between
  spec and implementation. Common in spec-first shops; we are
  implementation-first because FastAPI gives us the spec for free.
- **gRPC or another RPC framework with native code generation
  (Connect, tRPC).** All would work. Rejected because: gRPC is heavy for
  a small REST surface, tRPC is JavaScript-only and the CLI would still
  need its own client, and Connect would force a Buf-based toolchain on
  a project where the API maintainer already knows FastAPI.

## Consequences

**Easier:**

- Adding an endpoint becomes mechanical: edit Python, run
  `task gen:types`, commit the diff. The two clients update for free.
- Drift between server and client is structurally impossible to commit:
  CI's `gen-types-check` job blocks the PR.
- New contributors to the web or CLI app can rely on types being
  accurate; the generated file is the contract.

**Harder:**

- The pipeline has prerequisites (uv, pnpm, oapi-codegen) that must be
  installed before `task gen:types` works. Documented in
  [`docs/recipes/local-development.md`](../recipes/local-development.md).
- We are bound by what the generators support. See ADR
  [0005](0005-openapi-30-downgrade.md) for the OpenAPI 3.0 downgrade
  workaround that this decision forces.
- Any breaking schema change requires regenerating clients and updating
  consuming code in the same PR. This is a feature, not a bug, but it
  enlarges the diff.

**New constraints:**

- The generated files (`packages/api-types/src/index.ts` and
  `apps/cli/internal/apiclient/client.gen.go`) are not hand-edited.
  They have "do not edit" comments at the top.
- The pipeline must remain deterministic: same input schema produces
  the same generated output. Any change to generator versions or
  configuration is itself a decision worth recording.
